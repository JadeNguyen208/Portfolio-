Case Study 01 · Live Product

Designing for Drowsy Users

This is a live product, not a concept. SleepSoundMixer shipped on Product Hunt, monetised, and built entirely solo — design, code, marketing.

RoleSolo Designer & Developer
StackVanilla JS · Web Audio API · Canvas
StatusLive · Monetised
ScopeUX · Dev · Launch · Marketing
01 — The Problem

The Problem Worth Solving

Ambient sound apps exist. But most of them were designed for bright-screen, alert users — the same interaction model as a music app or podcast player. The actual use case is the opposite: 1AM, lights off, someone fighting insomnia, needing to hit play without waking up their brain.

The tension I started with: how do you design a low-friction UI for a user whose cognitive state actively works against them? Every extra tap, every label that requires reading, every screen-mode toggle adds friction at the worst possible moment.

"The best interaction for a drowsy user is no interaction at all — but since that's not possible, every design decision should minimise the cost of being awake."

02 — Constraints

Constraints as Creative Fuel

No budget. No team. No client deadline. This sounds like freedom, but self-imposed constraints are harder — there's no one to push back, no brief to anchor decisions. I had to create my own structure.

The rules I set: no third-party libraries for audio or animation, ship in 6 weeks, the UI must work one-handed on a 375px screen in the dark.

ConstraintWhy I kept itWhat it produced
No audio libraryControl over crossfade + mixCustom Web Audio API graph with per-channel gain nodes
No animation libraryPerformance on low-end mobileHand-tuned requestAnimationFrame loops, particle systems from scratch
One-hand mobile firstThe actual use caseAll primary controls in thumb-reach zone, large tap targets
03 — Audio-Visual Coupling

The Audio-Visual Coupling Problem

When a user activates Rain + Ocean simultaneously, two visual systems run at once. The naive solution: layer them. The problem: two independent animation loops fight for visual dominance.

The solution was a blend state system: each scene has a dominance weight (0–1). When two scenes are active, their visual outputs are alpha-composited based on their relative volume levels.

The insight: volume is already a proxy for user intent. If they've turned Rain up to 80% and Ocean to 20%, they've already told me which visual should dominate.

04 — Monetisation as UX

The Paywall Is a UX Decision

The question wasn't "where do we put the paywall" — it was "what friction is acceptable at what point in the user's journey, and why?" The final choice: the paywall triggers at session resume after the free hour expires, not during.

Free-to-paid flow3-tier pricingPayPal integrationSocial proof designZero signup friction
05 — i18n as Systems Thinking

5 Languages, 1 Layout

i18n is not translation. German runs ~30% longer than English. Vietnamese diacritics affect line-height. Chinese has no word-break spaces. Each is a layout bug waiting to happen.

My approach: build every component with the assumption that text content is unpredictable. That meant no fixed-width text containers, fluid button sizing, and a line-height system that accommodates diacritics without vertical rhythm breaking.

06 — Outcome

What Shipped & What I Learned

5Languages supported
9Sound scenes
3Pricing tiers
What I'd do differently

Conversion rate was lower than projected. The free tier was too generous — one hour per day reduces upgrade incentive. I'd shorten the free session to 20 minutes and add a "save your mix" feature locked behind Pro.

The second thing: I underinvested in onboarding. First-time users didn't understand they could mix multiple sounds simultaneously.

Case Study 02 · Concept Project

When the Medium Is the Message

A fictional luxury fruit brand built to answer one question: can 3D geometry alone — no photography, no copy — communicate premium value?

Role3D Art Direction · WebGL Dev
StackThree.js r128 · GLSL · CSS3D
TypeConcept · Self-initiated
ConstraintZero textures · Pure material
01 — The Brief

The Brief Underneath the Brief

Every luxury fruit delivery brand uses the same playbook: lifestyle photography, clean sans-serif type, pale green or cream backgrounds. The visual language is indistinguishable.

The real brief: make someone feel the price is justified before they read a single word. 3D was the answer because it most directly communicates craft — the sense that something was made by hand with intention.

02 — The No-Texture Decision

Why No Textures

Photo-realistic textures create a documentary feeling. Flat-shaded low-poly geometry says something different: this is a deliberate representation. It implies an artist made a choice — the same reason luxury brands use illustration over photography.

The no-texture constraint also had a practical payoff: zero texture loading time, consistent rendering across devices, and total control over color. The orange is exactly #ff8c42, not "orange-ish depending on jpeg compression."

03 — Motion as Hierarchy

Animation Timing as Visual Language

The three fruits float at different speeds: 3.2s, 2.8s, 3.6s. This is deliberate hierarchy. The orange (primary product) moves at the median speed, creating stability. The lemon is slightly faster, creating energy. The watermelon is slowest, anchoring the composition.

ObjectDurationRole in composition
Orange3.2sFocal point — median speed, visual anchor
Lemon2.8sEnergy — fastest, creates movement contrast
Watermelon3.6sAnchor — slowest, grounds the floating system
04 — Performance vs Beauty

The Mobile Tradeoff

I set a performance budget before writing any Three.js code: 60fps on a device with 4GB RAM and a mid-tier GPU, at 1080p.

Low-poly geometry (subdivision level 2) was the primary lever. The bloom post-processing effect was cut entirely for mobile — it adds a full render pass that drops mobile framerates below 45fps. The fallback is a CSS box-shadow approximating the glow at near-zero cost.

What doesn't work — and why I kept it

OrbitControls (mouse-drag rotation) feels great on desktop but is disorienting on touch — swipe to scroll conflicts with drag to rotate. I kept it desktop-only. The desktop experience is meaningfully richer; the mobile experience is still complete.

Case Study 03 · UI Design

Density Without Chaos

A high-density dark UI for internal team task tracking. The design challenge wasn't aesthetics — it was information architecture at the limit of what a single screen can hold.

RoleUI Design · Frontend Dev
StackCSS Grid · Vanilla JS
TypeInternal Tool · No Framework
System8px grid · Tabular type
01 — Defining Density

What "High Density" Actually Means

Density in UI isn't about fitting more elements on screen. It's about the ratio of useful information to visual noise. I started by mapping the information hierarchy: what does a team member need to know in the first 3 seconds?

Density is not a quantity problem. It's a hierarchy problem. The question isn't "how many things can I show?" but "in what order does the user need to process them?"

02 — Color as Language

The Priority Color System

Red/Yellow/Green for priority is a convention so established it's almost invisible. My solution: color is never the only signal. Each priority level has a color, a text label, and a distinct background opacity — accessible to the ~8% with red-green color blindness.

PriorityColorLabelBackground
Urgent#f87171 (red)"Urgent"rgba(239,68,68,.18) — densest
Medium#fbbf24 (amber)"Medium"rgba(234,179,8,.18) — mid
Low / Done#86efac (green)"Low" / "Done"rgba(74,222,128,.15) — lightest
03 — Typography as Data

When Type Choices Are Functional, Not Aesthetic

Tabular numerals (font-variant-numeric: tabular-nums) on all dates and numbers — fixed-width glyphs let the eye scan columns rather than read individual values.

Space Mono for UI text — monospace means every character is predictably wide, which matters when task names truncate at inconsistent points. The layout is more stable under variable content.

04 — The No-Framework Decision

Vanilla CSS & JS — Why, and What It Costs

Why I chose it: For a static mockup demonstrating UI capability, a framework adds build complexity without adding demonstrable value. Vanilla implementation shows I understand what frameworks are abstracting.

What it costs: Drag-and-drop in vanilla JS is significantly more complex than with dnd-kit. Real-time collaboration would need a state management system painful to build without React or Vue.

Version 2 would look like this

React + dnd-kit for real drag-and-drop. Zustand for local state, with the option to add a WebSocket sync layer later. The 8px grid system and color language would remain unchanged — those are design decisions, not implementation decisions.

05 — Outcome

What This Project Demonstrates

8pxGrid system — every spacing value
3×Redundant encoding per priority
0Dependencies — pure CSS & JS

The dashboard demonstrates IA thinking, accessibility consideration, and the ability to make and articulate intentional technical tradeoffs.
